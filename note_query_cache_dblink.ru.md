# Сценарий 6: DBLink + query cache на внешнем кластере

Проверка гипотезы «на внешнем кластере можно подкрутить кэширование и снять
нагрузку с основного». Всё измерено на стенде `s1`, ClickHouse `26.3.17.110`.
Полный протокол с запросами и выводом — `scratch_queries_query_cache.sql`.

Стенд: `main_cluster` (2 шарда × 2 реплики, `default.events_local` +
`events_distributed`, read-only УЗ `ro_export_user`), внешняя нода
`ch-ext-s1r1` — одиночный узел, своих данных не хранит, только проксирует
запросы.

## Вердикт

Гипотеза подтверждается — повторный идентичный запрос обслуживается целиком
на ext: **20–41 мс → 1 мс**, и в основной кластер не уходит ни одного
подзапроса. Но **профиль из гипотезы в таком виде не кэширует ничего**, а
способ поднять hit-rate, указанный как компромисс, оказался дырой в правах
доступа. Ниже по порядку.

## Как сделан линк

`Distributed`-таблица на ext поверх кластера, объявленного в конфиге ext:

```xml
<!-- docker/s1/config.d/common-ext.xml, внутри <remote_servers> -->
<main_link>
    <shard><internal_replication>true</internal_replication>
        <replica><host>ch-main-s1r1</host><port>9000</port>
            <user>ro_export_user</user><password>***</password></replica>
        <replica><host>ch-main-s1r2</host>...</replica>
    </shard>
    <shard>... ch-main-s2r1, ch-main-s2r2 ...</shard>
</main_link>
```

```sql
CREATE TABLE ext.link_events_dist
(
    ts DateTime, user_id UInt64, event_type LowCardinality(String),
    value Float64, ingested_at DateTime
)
ENGINE = Distributed(main_link, default, events_local, rand());
```

Конфиг подхватывается на лету, рестарт не нужен — кластер сразу виден в
`system.clusters`. Читателю нужен только `GRANT SELECT` на таблицу; ходить
в основной кластер как-то иначе он не может. Плата — пароль источника лежит
в конфиге ext открытым текстом.

Важное следствие для замеров: линк идёт по двум шардам, поэтому **один запрос
пользователя = 2 подзапроса на main**. Все цифры ниже — в подзапросах.

## Профиль из гипотезы не кэширует ничего

```sql
query_cache_min_query_duration = 1000   -- «не мусорить лёгкими запросами»
```

Запросы через линк идут 20–41 мс. Порог в 1000 мс отсекает их все:

| профиль | hits/misses на ext |
|---|---|
| как в гипотезе | 0/1 (41 мс), 0/1 (20 мс) — оба в источник |
| `query_cache_min_query_duration = 0` | 0/1 (25 мс), затем **1/0 (1 мс)** — второй не дошёл до main |

Правильный инструмент для «не мусорить одноразовыми запросами» —
`query_cache_min_query_runs`, он считает **повторы**, а не длительность.
Проверено: при `= 2` прогоны 1–3 промахиваются (третий пишет запись, 6
подзапросов на main), с четвёртого идут попадания за 1 мс. Дашборд с
фиксированным набором фильтров проходит этот фильтр, ad-hoc — нет, и при этом
быстрые запросы не выбрасываются.

Мелочь в плюс: ключ кэша — это AST, а не текст. Тот же запрос,
переформатированный с переносами строк, попадает в ту же запись.

## Сколько нагрузки реально уходит

3 пользователя × 5 идентичных запросов; считались запросы `ro_export_user` на
**всех четырёх** узлах main:

| сценарий | подзапросов на main | hits/misses на ext |
|---|---|---|
| A. кэш выключен | 30 | 0/0 |
| B. кэш включён, изоляция по пользователям (по умолчанию) | 22 | 4/11 |
| C. `query_cache_share_between_users = 1` | **2** | 14/1 |
| D. один технический пользователь | **2** | 14/1 |

То есть «из коробки» кэш снимает ~27% нагрузки, а не 90%. Середины нет:
либо все читатели — один принципал, либо hit-rate остаётся низким.

## Изоляция по пользователям хуже, чем «каждый греет свой кэш»

Это не «у каждого своя копия записи». Пока ключом владеет пользователь A,
результаты пользователя B **не кэшируются вообще**: B промахивается каждый раз,
а в `system.query_cache` так и остаётся одна запись. Проверено — 3
дополнительных прогона от B дали 3 похода в источник и по-прежнему одну запись
в кэше. В таблице выше это видно по строке B: 4 попадания на 15 запросов —
это ровно 4 повтора одного пользователя A, остальные 11 запросов ушли в main.

Кто владеет записью, решает первый писатель. Флаг `share_between_users`
проверяется **на записи**: если писатель поставил `= 1`, запись помечается
`shared = 1`, и читателям ставить у себя ничего не нужно.

## `share_between_users = 1` — это не «не рекомендуется», это дыра

Два измеренных факта:

1. **Гранты не проверяются на попадании в кэш.** Пользователь без единого
   гранта (`SHOW GRANTS` пустой) выполнил тот же запрос и получил `9810` — тот
   же результат, что и пользователь с грантом. Не `ACCESS_DENIED`, а данные.
   Тот же пользователь, та же таблица, но запрос, которого нет в кэше:
   `Code: 497 ... necessary to have the grant SELECT ON ext.link_events_dist`.
   То есть права работают нормально — их пропускает именно попадание в кэш.

2. **Row policy обходится.** У `bi_user2` политика `event_type = 'click'`, его
   честный ответ — `1843`. Прочитав общую запись, прогретую другим
   пользователем, он получил `10915` — полную таблицу.

```
bi_user  прогревает : 10915
bi_user2 читает     : 10915     <- видит всё
bi_user2 правда     :  1843     (тот же запрос с use_query_cache = 0)
```

Для внешнего кластера с десятками пользователей это не компромисс, а
эскалация прав. Единственный безопасный путь к тем же цифрам — один
технический пользователь на BI-прокси (вариант D), где все читатели и так
один принципал.

## Тихие невключения кэша

Ни одно из них не логируется и не отдаёт предупреждения:

- **Результат больше `max_entry_size_in_bytes` (1 MiB).** 2 млн строк — запись
  не создаётся, каждый прогон промах. И это не бесплатно: `QueryCacheWrittenRows`
  вырос на 4 млн, `QueryCacheWrittenBytes` — на 64 МБ. Результат каждый раз
  сериализуется в буфер кэша и выбрасывается.
- **Пользовательские квоты** `query_cache_max_entries` / `query_cache_max_size_in_bytes`.
  При `max_entries = 1` первый запрос кэшируется, все последующие — никогда.
- **`query_cache_nondeterministic_function_handling = 'ignore'`** — запрос
  выполняется, запись не создаётся.

Серверные лимиты по умолчанию: 1 GiB на весь кэш, 1024 записи, 1 MiB и
30 млн строк на запись.

## `now()` / `today()`: по умолчанию не «отключает кэш», а роняет запрос

```
Code: 704. The query result was not cached because the query contains a
non-deterministic function. Use setting
`query_cache_nondeterministic_function_handling = 'save'` or `= 'ignore'`
(QUERY_CACHE_USED_WITH_NONDETERMINISTIC_FUNCTIONS)
```

Дефолт — `throw`. То есть включение `use_query_cache = 1` в профиле мгновенно
ломает **все** дашбордные запросы с `now()`, пока не выставлен `save` или
`ignore`. Это самая опасная строчка при раскатке на живых пользователей.

С `'save'` значение замерзает на весь TTL — проверено, три вызова `now()` с
интервалом 2 с вернули одну и ту же секунду. Для запроса вида
`WHERE ts > now() - INTERVAL 1 HOUR` это значит, что окно перестаёт ехать:
пользователь видит час, посчитанный от замороженного момента. Практичнее
ставить `'ignore'` (запросы с `now()` просто не кэшируются, без ошибок), а
дашбордам отдавать границы окна литералами со стороны BI — тогда запрос
детерминирован и кэшируется честно.

Отдельно: системные таблицы по умолчанию тоже `throw` —
`Code: 719 QUERY_CACHE_USED_WITH_SYSTEM_TABLE`.

## TTL, протухание, точечная инвалидация

TTL по умолчанию 60 с, в профиле меняется. Запись после истечения не исчезает,
а помечается `stale = 1`, следующий запрос идёт в источник. Проверка на
TTL = 15 с прошла ровно так: `expires_at` = момент записи + 15 с, через 17 с
`stale = 1`, следующий прогон — 2 подзапроса на main.

Staleness — это и есть плата: закэшировал `12000`, долил на main 400 строк,
ext продолжал отвечать `12000` до конца TTL. Точечно сбрасывается тегом:

```sql
SELECT ... SETTINGS query_cache_tag = 'events_dash';
SYSTEM DROP QUERY CACHE TAG 'events_dash';   -- после этого сразу 12400
```

## Настройки лучше пинить, а не надеяться на readonly

С `Distributed`-линком работают оба режима, но по-разному:

- `readonly = 1` — пользователь не может передать вообще никаких `SETTINGS`.
  Кэш из профиля при этом работает (промах 36 мс → попадание 1 мс). Минус:
  многие BI-инструменты сами шлют настройки (`max_execution_time` и т.п.) и
  будут падать с `Code: 164`.
- `readonly = 2` — настройки менять можно, а значит пользователь спокойно
  сделает `SETTINGS use_query_cache = 0`.

Пинится это константным ограничением в профиле:

```sql
CREATE SETTINGS PROFILE external_readers SETTINGS
    readonly = 2,
    use_query_cache = 1 CONST,
    query_cache_min_query_runs = 2,          -- вместо min_query_duration
    query_cache_min_query_duration = 0,
    query_cache_ttl = 300,
    query_cache_nondeterministic_function_handling = 'ignore' CONST,
    query_cache_share_between_users = 0 CONST;
```

`SETTINGS use_query_cache = 0` от такого пользователя →
`Code: 452 SETTING_CONSTRAINT_VIOLATION`, а неконстантный `query_cache_ttl`
остаётся переопределяемым (это и нужно — тяжёлым выгрузкам можно дать больше).

## Операционные свойства

- **Пока запись горячая, ext отвечает при полностью лежащем источнике.**
  Погасил все четыре узла main — закэшированный запрос отдал полный результат,
  незакэшированный упал с `Code: 279 All connection tries failed`. Для внешнего
  кластера это бонус, который репликация даёт иначе и дороже.
- **Кэш живёт в памяти процесса.** После `docker restart` ext — 0 записей,
  первый же запрос идёт в источник. Никакого прогрева при старте нет,
  его надо делать самому (крон с набором дашбордных запросов).
- Один кэш на процесс: у нас 1 узел, поэтому история со sticky-роутингом
  действительно не актуальна.

## Мониторинг

- `system.query_cache`: `query, query_id, result_size, tag, stale, shared,
  compressed, expires_at, key_hash`. Колонки `is_subquery` в 26.3 нет.
- `system.metrics`: `QueryCacheBytes`, `QueryCacheEntries`.
- `system.events`: `QueryCacheHits`, `QueryCacheMisses`, `QueryCacheAgeSeconds`,
  `QueryCacheReadRows/Bytes`, `QueryCacheWrittenRows/Bytes`.
- Поштучно: `ProfileEvents['QueryCacheHits' / 'QueryCacheMisses']` в `query_log`.

Практический индикатор проблемы: `QueryCacheWrittenBytes` растёт, а
`QueryCacheEntries` — нет. Значит результаты не влезают в `max_entry_size_in_bytes`
и сериализуются впустую.

## Итог по гипотезе

Кэш действительно снимает нагрузку, но только на повторяющихся байт-в-байт
запросах и только если читатель — один принципал. Рабочая конфигурация:
BI-прокси под одним техническим пользователем + профиль с `CONST`-пинами +
`min_query_runs` вместо `min_query_duration` + `'ignore'` для
недетерминированных функций + литеральные границы окон вместо `now()`.
Ad-hoc аналитика мимо кэша пролетает целиком — тут гипотеза ничего не меняет.

- В `docker/s1/config.d/common-ext.xml` добавлен кластер `main_link` (4 узла
  main, пользователь `ro_export_user`, **пароль открытым текстом**).
- На ext созданы: таблица `ext.link_events_dist`, профили `external_readers`,
  `external_readers_ro`, `external_readers_ro2`, `external_readers_const`,
  `quota_probe`, пользователи `bi_user`, `bi_user2`, `bi_user3`, `bi_ro`,
  `bi_ro2`, `bi_const`, `bi_quota`, `bi_nogrant`.
- На main дозалито 700 строк с `event_type = 'cache_probe'` / `'cache_probe2'`
  (проверка протухания), итого 12400.
- Refreshable MV из сценария 5 (`ext.events_sync`, `ext.dim_users_sync`)
  остановлены: после рестарта ext они возобновились сами
  (`stop_refreshable_materialized_views_on_startup = 0`) и опрашивали main
  каждые 10 с, что портило замеры. Сейчас `Disabled`, фоновый трафик к main — 0.
