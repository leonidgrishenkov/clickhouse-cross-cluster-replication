> **Примечание о версии (обновление после исследования)**: файлы Docker
> Compose и Makefile в этом репозитории зафиксированы на версии
> `26.3.17.110` (26.3 LTS). Всё, что описано ниже, — каждое измерение,
> каждое сообщение об ошибке и каждое описанное поведение — было получено
> на версии `25.8.30.16` (25.8 LTS), которая фактически использовалась при

## 1. Границы задачи, методика и окружение

**Цель**: определить, способны ли штатные механизмы ClickHouse
реплицировать данные из продакшн-кластера с шардированием в отдельный,
максимально изолированный внешний кластер для внешних пользователей с
доступом только на чтение, и если да, то какой механизм и при каких
условиях следует выбирать.

**Версия**: `clickhouse/clickhouse-server:25.8.30.16` /
`clickhouse/clickhouse-keeper:25.8.30.16`. 25.8 — текущая LTS-ветка
(выпущена 2025-08-28). Проверено по:
- https://clickhouse.com/docs/resources/changelogs/oss/2025 (открыто в ходе
  этой исследовательской сессии)
- https://endoflife.date/clickhouse (25.8 LTS показана как активная, 25.3
  LTS — как предыдущая; обе страницы открыты в той же сессии)
- список тегов Docker Hub для `clickhouse/clickhouse-server`,
  подтверждающий, что `25.8.30.16` — последний патч ветки 25.8 на момент
  исследования.

Оба образа были загружены, и `SELECT version()` подтвердил `25.8.30.16` на
каждом контейнере в каждом сценарии.

**clickhouse-copier**: по данным OSS-changelog и независимых источников
(статья на oneuptime.com, датированная 2026-03-31; сверено с записями
OSS-changelog за 2024 год) подтверждено, что инструмент больше активно не
поддерживается и не поставляется вместе с современными серверными
пакетами — он вынесен в отдельный репозиторий `ClickHouse/copier`. Не
собирался согласно указанию в задании; зафиксирован исключительно как факт
из документации.

**Песочница**: 4 vCPU, 7,8 ГБ RAM, 144 ГБ диска, Docker 29.7.2 /
Compose v5.4.0. Простаивающий одиночный узел ClickHouse потреблял примерно
224 MiB RSS / ~6% CPU (лимит `--memory=600m`, замер через 10 с после
старта). Сценарии запускались по одному (не все девять одновременно),
чтобы каждому доставался полный бюджет ресурсов; явный перечень отклонений
от значений по умолчанию, заданных в задании, приведён в README.md.

**Единая методика, применённая к каждому сценарию** (что конкретно
проверялось, а что нет, см. в разделе соответствующего сценария):
1. Поднять окружение, загрузить данные, подтвердить исходную
   согласованность.
2. Нагрузка вставками (пакеты от 2 тыс. до 500 тыс. строк; НЕ непрерывный
   поток 30–100 тыс. строк/с в течение 15+ минут — почему именно так и как
   вместо этого экстраполировались затраты на строку, см. в разделе
   допущений в README.md).
3. Мутации (ALTER UPDATE/DELETE), OPTIMIZE FINAL, ADD COLUMN, DROP
   PARTITION — зафиксированы факт распространения и тайминги.
4. Хаос-тесты: остановка/запуск узла, отключение/подключение сети,
   остановка Keeper (S1c), рост диска во время недоступности (S3),
   «бомбардировка» запросами (S1, S9).
5. Согласованность: `count()` и `sum(cityHash64(*))` по партициям, с FINAL
   и без него, сравнение main и ext.
6. Тест изоляции: со стороны «внешнего» кластера — попытки достучаться до
   узлов main, выполнить INSERT/ALTER/SYSTEM, прочитать
   `system.zookeeper`.

## 2. S1 — внешний узел как дополнительная реплика той же ReplicatedMergeTree

### 2.1 Топология

2 шарда × 2 реплики на main (`ch-main-s1r1/s1r2/s2r1/s2r2`), 2 шарда с
одной репликой на ext (`ch-ext-s1r1/s2r1`), общий ансамбль Keeper из 3
узлов (`keeper-1/2/3`). `docker/s1/docker-compose.yml`. Узлы ext
подключены к сети `net-ext` и к общей сети `net-repl` вместе с main и
Keeper; при этом они **не** перечислены в `remote_servers` кластера main
вообще — у них собственное определение `ext_cluster` для их собственных
таблиц `Distributed` (в этом проходе не строилось, но конфигурация это
поддерживает — см. `config.d/common-ext.xml`).

### 2.2 Рецепт с UUID/macros (задокументированная «главная практическая ловушка»)

«Голая» `ReplicatedMergeTree` (без явных аргументов движка) использует
`default_replica_path = /clickhouse/tables/{uuid}/{shard}`, где `{uuid}`
раскрывается в собственный случайно сгенерированный UUID таблицы в базе
данных с движком `Atomic`. Подтверждено экспериментально: попытка
использовать «голую» форму завершается ошибкой —
`Code: 36. BAD_ARGUMENTS: Macro 'uuid' in engine arguments is only
supported when the UUID is explicitly specified, used within an ON CLUSTER
query, or when using the Replicated database engine` — ЕСЛИ ТОЛЬКО вы не
(а) выполните CREATE через `ON CLUSTER` по кластеру, включающему обе
группы (что нарушает цель изоляции «ext отсутствует в remote_servers» для
этого одного оператора), либо (б) не укажете `UUID '...'` явно на каждой
реплике, чтобы они совпали, либо (в) не используете движок базы данных
`Replicated` (он автоматически обеспечивает согласование UUID; в этом
проходе не оценивался как S2, см. §9).

**Рецепт, фактически применённый и рекомендуемый (полностью обходит
ловушку)**: использовать ЯВНЫЕ аргументы движка с путём на основе macros,
который вообще не зависит от `{uuid}`:
```sql
CREATE TABLE testgame.events
(...)
ENGINE = ReplicatedMergeTree('/clickhouse/tables/{shard}/testgame/events', '{replica}')
...
```
с macros, заданными для каждого узла:
```xml
<!-- ch-main-s1r1 -->
<macros><shard>1</shard><replica>main_r1</replica></macros>
<!-- ch-ext-s1r1 -->
<macros><shard>1</shard><replica>ext_r1</replica></macros>
```
Оба варианта раскрываются в ОДИН И ТОТ ЖЕ zoo_path
(`/clickhouse/tables/1/testgame/events`) при РАЗНЫХ именах реплик.
Работоспособность подтверждена сквозным тестом: INSERT на `ch-main-s1r1`
появился на `ch-ext-s1r1` в течение 5 секунд, а `system.replicas` с обеих
сторон показала все зарегистрированные имена реплик (`main_r1`, `main_r2`,
`ext_r1`) для таблицы шарда 1.

### 2.3 S1a (полноправная реплика) и S1b (настройка режима «только follower»)

**S1a подтверждено**: узел ext является настоящей полноценной репликой —
читает, выполняет слияния, может стать лидером (`is_leader=1` по
умолчанию) и **может принимать записи, которые распространяются обратно на
main** (подтверждено: INSERT, выполненный напрямую на `ch-ext-s1r1`,
появился на `ch-main-s1r1` в течение 5 с). Это важнейшая оговорка по S1:
сам механизм репликации не даёт НИКАКОЙ изоляции по записи. Свойство
изоляции (в) — «внешние пользователи не должны иметь возможности писать
или изменять данные» — целиком лежит на уровне пользователей/профилей, а
не на топологии репликации.

**Настройки S1b, наличие которых в 25.8.30.16 проверено перед
использованием** (через `system.merge_tree_settings` / `system.settings` в
работающем контейнере):

| Настройка | Область | По умолчанию | Проверено |
|---|---|---|---|
| `always_fetch_merged_part` | на таблицу (MergeTree) | `0` | СУЩЕСТВУЕТ |
| `replicated_can_become_leader` | на таблицу (MergeTree) | `1` | СУЩЕСТВУЕТ |
| `max_concurrent_queries_for_user` | на пользователя (settings) | `0` (без ограничений) | СУЩЕСТВУЕТ |
| `max_memory_usage`, `max_execution_time`, `readonly` | на пользователя (settings) | стандартные для версии | СУЩЕСТВУЮТ |

Применено через `ALTER TABLE testgame.events MODIFY SETTING
replicated_can_become_leader = 0` на реплике ext — эффект подтверждён:
`system.replicas.can_become_leader` изменилось с `1` на `0`. Был создан
выделенный пользователь `ext_reader` (`profile=ext_readonly`, `readonly=1`,
`max_concurrent_queries_for_user=10`, квота с окном 60 с / 1000 запросов)
(`docker/s1/users.d/users-ext.xml`) и протестирован:

- SELECT: выполняется успешно.
- INSERT / `ALTER ... DELETE`: отклоняется с `Code: 164. READONLY`.
- `SYSTEM DROP REPLICA`: отклоняется с `Code: 497. ACCESS_DENIED`.
- `SELECT ... FROM system.zookeeper WHERE path=...`: **выполняется
  успешно** — это настоящая брешь в изоляции: `readonly=1` НЕ ограничивает
  доступ к `system.zookeeper`, раскрывая внутреннюю топологию реплик и
  пути основного кластера любому внешнему пользователю с правами только на
  чтение. **Исправление (ещё не протестировано, зафиксировано как
  обязательная мера усиления защиты)**: явный
  `REVOKE SELECT ON system.zookeeper FROM ext_reader` либо выдача `SELECT`
  только на `testgame.*` с самого начала вместо наследования широких
  прав по умолчанию.

### 2.4 S1c — раздельный Keeper: подтверждено, что схема полностью не работает

Был поднят независимый одноузловой Keeper (`keeper-ext-1`, собственная
`raft_configuration`), блок `<zookeeper>` узла `ch-ext-s2r1` был
переключён на него при СОХРАНЕНИИ идентичной строки zoo_path
(`/clickhouse/tables/2/testgame/events`). Результат: **нулевой обмен
данными в обе стороны** — вставка на узле с раздельным Keeper так и не
достигла main, и наоборот. Идентичная строка zoo_path не имеет никакого
смысла между двумя независимыми кластерами Keeper; общая репликация
возникает, только когда путь разрешается внутри ОДНОГО И ТОГО ЖЕ
физического ансамбля. **Это даёт окончательный ответ на вопрос
«приемлем ли общий Keeper» именно для S1: он не опционален, он структурно
обязателен.** В этом и состоит основная цена изоляции при подходе S1:
работоспособность и поведение внешней реплики навсегда завязаны на ТОТ ЖЕ
ансамбль Keeper, который обслуживает продакшн-трафик.

### 2.5 Направление трафика и нагрузка на interserver

`system.replicated_fetches` и `ReplicatedPartFetches` (system.events)
подтвердили, что реплика ext ЗАБИРАЕТ (fetch) части с main (ожидаемо: в
большинстве тестов вставки выполнял main). Обратный трафик (main забирает
с ext) тоже наблюдался — один раз, потому что вставка, выполненная прямо
на ext, породила данные, которые затем пришлось забирать main. Это
подтверждает, что **встроенной гарантии того, что продакшн-узлы никогда не
станут ИСТОЧНИКОМ fetch для внешних, не существует**: любая реплика,
включая узлы main, обслужит запрос на получение части от любой другой
реплики той же таблицы — main или ext, без различия. Единственный способ
структурно запретить main когда-либо обслуживать ext — это изоляция по
записи через пользователя readonly (§2.3) в сочетании с настройками
`always_fetch_merged_part`/`replicated_can_become_leader` (которые снижают,
но не устраняют способность ext стать источником слияний/частей для main,
поскольку эти настройки управляют ИСХОДЯЩИМ поведением самого ext, а не
готовностью main принять запрос на fetch ОТ ext).

### 2.6 DDL: уточнение предполагаемого в задании риска

**Измерено**: `ALTER TABLE testgame.events ADD COLUMN yet_another_field
UInt8 DEFAULT 0`, выполненный как обычный (не `ON CLUSTER`) ALTER прямо на
`ch-main-s1r1`, распространился на `ch-main-s1r2` (тот же шард, входит в
`main_cluster`) И на `ch-ext-s1r1` (тот же шард, явно НЕ входящий в
`remote_servers` кластера `main_cluster`) в течение 3 секунд — но НЕ достиг
`ch-main-s2r1` (другой шард). Тот же результат для `ALTER ... DROP
PARTITION` и мутаций `ALTER ... UPDATE/DELETE`.

**Почему**: для `ReplicatedMergeTree` эти типы ALTER сами по себе являются
записями в СОБСТВЕННЫЙ лог репликации таблицы по её пути zoo_path в
Keeper — тот же самый механизм, который распространяет INSERT. `ON
CLUSTER` тут ни при чём; это лишь удобство, позволяющее за один
клиентский round-trip разослать ОДИН И ТОТ ЖЕ текст DDL на N хостов,
перечисленных в определении кластера.

**Скорректированная формулировка для отчёта** (опровергает тезис задания
«DDL: ON CLUSTER по main не затронет ext -> риск расхождения схем» как
безусловное утверждение): расхождение схем — реальный риск ТОЛЬКО для
DDL, который не проходит через лог репликации: `CREATE TABLE`/`DROP
TABLE`/`RENAME TABLE` (они создают/уничтожают тот самый znode-путь, за
которым ведётся наблюдение), а также DDL по нереплицируемым объектам
(обычный `MergeTree`, словари, таблицы `Distributed`, представления). Для
ЭТИХ случаев единственное решение — `ON CLUSTER` с кластером,
включающим обе группы (собран как `all_nodes_ddl` в
`config.d/common-main.xml`, протестирован только на шаге создания), либо
ручной оператор на каждом узле, и это действительно требует уступки в
изоляции (конфигурация main должна содержать имена хостов ext, чтобы такая
запись о кластере вообще существовала). Но для обычных ALTER схемы на уже
реплицируемых таблицах никакие обходные пути не нужны вовсе.

### 2.7 Хаос-тесты и тесты обратного влияния (полные детали в LOG.md)

| Тест | Результат |

### 2.8 Безопасность

`interserver_http_credentials` (общий секрет между main и ext для
аутентификации при получении частей) был настроен и обязателен — без него
interserver-вызовы по HTTP между произвольными узлами в одной сети
проходили бы без аутентификации. Для самого Keeper в этой песочнице ACL не
настраивались (ClickHouse Keeper по умолчанию не применяет ACL, пока они
не сконфигурированы явно через `four_letter_word_allow_list` и
собственные ACL Keeper; в этом проходе не оценивалось — отмечено как
пункт усиления защиты для продакшена). Необходимые порты для S1:
клиентский порт Keeper (9181, ext→keeper), interserver HTTP (9009,
двунаправленно в зависимости от направления fetch). Нативный клиентский
порт (9000) между ext и main должен быть полностью закрыт файрволом (для
самой репликации он не нужен, только для прямого SQL-доступа, который
должен идти через собственный слушатель ext, а не main).

## 3. S6 — BACKUP/RESTORE в S3 (MinIO)

### 3.1 Топология

Два ПОЛНОСТЬЮ независимых одноузловых кластера (`ch-main` +
`keeper-main-1`; `ch-ext` + `keeper-ext-1`), без общего Keeper и без общей
сети между ними после исправления топологии (см. §3.5). MinIO и `mc`
предоставляют S3-бакет, подключённый сразу к двум непересекающимся
bridge-сетям, так что каждая сторона достаёт до него, не достигая другой
стороны.

### 3.2 Полный и инкрементальный бэкап — измерения

| Метрика | Полный бэкап | Инкрементальный (`base_backup=...`) |
|---|---|---|
| Время выполнения | 0,271 с | 0,452 с |
| `num_files` | 55 | 69 |
| `uncompressed_size` | 6 724 796 Б | 7 577 103 Б |
| Данные | 300 000 строк, 4 партиции | +50 000 строк, `ALTER UPDATE` на 1 строку |

RESTORE: 0,505 с для всей базы данных; построчная согласованность
подтверждена (`count()` и `sum(cityHash64(*))` по партициям идентичны с
обеих сторон).

**Ключевой вывод**: «инкрементальный» бэкап оказался лишь немногим меньше
полного, потому что `ALTER TABLE ... UPDATE`, затронувший всего одну
строку, переименовал КАЖДУЮ активную часть (инкремент суффикса версии
мутации, например `20260816_0_0_0` → `20260816_0_0_0_1`), хотя фактическое
байтовое содержимое 3 из 4 партиций не изменилось. `BACKUP ...
base_backup=...` дедуплицирует на уровне ЧАСТЕЙ (части с неизменившимися
именем и контрольной суммой пропускаются), а не на уровне строк или байт —
любая операция, переименовывающая части по посторонним причинам (мутации,
`OPTIMIZE FINAL`, слияния), сводит на нет эффективность инкрементального
бэкапа именно для этих партиций. **В этой версии действительно есть
`enable_lightweight_update=1` (включена по умолчанию) как более новый
альтернативный механизм мутаций, нацеленный на избежание полной
перезаписи частей; но избавляет ли он именно от этого эффекта раздувания
бэкапа, в этом проходе НЕ проверялось** — отмечено как задача на будущее,
а не как утверждение.

### 3.3 Бэкап на уровне партиций, подводные камни RESTORE и реально работающий рецепт

`BACKUP TABLE events PARTITION 'x' TO S3(...)` работает как описано в
документации. В предложенном в задании шаблоне «RESTORE во временную
таблицу + ATTACH/REPLACE PARTITION» обнаружились два настоящих тупика:

1. **`RESTORE ... SETTINGS allow_non_empty_tables=1` напрямую в живую
   непустую целевую таблицу НЕ идемпотентен.** Повторный запуск того же
   восстановления партиции продублировал все строки в этой партиции
   (81 226 → 212 452) — восстановленные части добавляются рядом с
   существующими, без какой-либо дедупликации. **Решение**: выполнять
   `ALTER TABLE events DROP PARTITION 'x'` непосредственно перед RESTORE,
   что делает цикл идемпотентным ценой короткого окна с пустой одной
   партицией (а не простоя всей таблицы).

2. **`RESTORE TABLE src AS dst` структурно нерабочий для источника
   `ReplicatedMergeTree` с литеральным (не через макрос `{table}`)
   zoo_path.** Пробовались три варианта (заранее созданная временная
   таблица с обычным `MergeTree`; заранее созданная временная таблица
   `ReplicatedMergeTree` с собственным отдельным zoo_path; создание
   временной таблицы самим RESTORE с нуля через `structure_only=1`) — ВСЕ
   ТРИ ПРОВАЛИЛИСЬ. Первые два — из-за несовпадения схемы
   (`CANNOT_RESTORE_TABLE`: RESTORE сверяется с ИСХОДНЫМ DDL из бэкапа,
   игнорируя фактическое определение таблицы-приёмника); третий —
   с ошибкой `Code: 253. REPLICA_ALREADY_EXISTS`, потому что RESTORE
   пересоздаёт таблицу ПО СОБСТВЕННОМУ zoo_path ИСТОЧНИКА, независимо от
   переименования через `AS`, и конфликтует с уже зарегистрированной
   репликой настоящей таблицы на том же узле. **Это означает, что
   предложенный в задании шаблон с временной таблицей не работает так, как
   заявлено** для таблицы, использующей ровно тот стиль zoo_path, который
   этот же отчёт рекомендует в другом месте (S1, §2.2) — две рекомендации
   частично противоречат друг другу, и отчёт говорит об этом прямо.
   Единственный протестированный и реально работающий рецепт обновления
   партиции с минимальным простоем в этой версии — шаблон
   DROP PARTITION, затем RESTORE из пункта 1 выше, а не
   «временная таблица + REPLACE PARTITION».

### 3.4 RESTORE на другую топологию шардов

Отдельным многошардовым тестом в этом проходе не проверялось (стенд S6 по
замыслу использовал одноузловые main/ext, чтобы изолировать сам механизм
BACKUP/RESTORE от многошардовых особенностей S1) — но механизм зависит от
схемы, а не от топологии: `RESTORE DATABASE` требует лишь совместимости
колонок и движка, и было подтверждено, что он успешно отрабатывает даже
когда main и ext независимо определяют макросы `{shard}`/`{replica}` как
`1`/`main_r1` и `1`/`ext_r1` соответственно (то есть «шард 1» на ext не
имеет никакого отношения к «шарду 1» на main, кроме выбранного человеком
значения макроса). Именно на этом основана оценка «лучшая гибкость по
топологии» в сравнительной матрице.

### 3.5 Тест изоляции выявил НАСТОЯЩИЙ дефект в топологии самого этого окружения

Изначально `ch-main` и `ch-ext` были помещены в ОБЩУЮ сеть (`net-s3`),
чтобы обе стороны могли достучаться до MinIO. Тест изоляции
(обязательный по единой методике) показал, что эта общая сеть ЗАОДНО дала
им полную взаимную достижимость: `ch-ext` мог выполнять `SELECT` из
таблиц `ch-main` И `INSERT` в них напрямую по нативному протоколу, под
пользователем по умолчанию с пустым паролем. **В первоначальном виде это
полностью разрушало главную предпосылку S6 — «бакет является единственной
точкой соприкосновения».**

**Исправление применено и перепроверено**: разделение на две
непересекающиеся bridge-сети (`net-s3-main`, `net-s3-ext`), MinIO
подключён к обеим. После исправления `ch-ext` вообще не может разрешить
имя `ch-main` (`getent hosts` пусто, `clickhouse-client --host ch-main` →
`Code: 198. DNS_ERROR`), тогда как `BACKUP`/`RESTORE` через MinIO
продолжили работать с обеих сторон без изменений (перепроверено новым
вызовом `BACKUP DATABASE` после исправления).

**Почему это важно за пределами песочницы**: это наглядная демонстрация
ошибки, которую легко допустить в реальной инфраструктуре — размещение
основных и внешних узлов ClickHouse в общей VPC/подсети «просто ради
доступа к S3» (общий NAT-шлюз, peering с общей сервисной VPC) может
незаметно воспроизвести ровно эту дыру. Тест изоляции — не формальность:
именно он выявил реальный дефект в окружении самого этого исследования.

## 4. S3 — push через Materialized View → Distributed

### 4.1 Топология

Main (один узел) + ext (один узел) в разных сетях с одним явным каналом
`net-push`, по которому идёт инициируемый со стороны main трафик INSERT на
порт нативного протокола ext (направление, противоположное pull-модели
S6/S7).

### 4.2 Механизм подтверждён

`INSERT INTO main.events` → срабатывает MV → запись в
`Distributed(ext_push_cluster, testgame, events, rand())` → данные попадают
на ext. Подтверждено как для одиночных вставок, так и для пакетов по
10 000 строк, задержка распространения около 3 с.

### 4.3 Дозагрузка истории и POPULATE — обнаружено настоящее жёсткое ограничение

Предупреждение из задания подтвердилось: исторические данные, находившиеся
в `main.events` ДО создания MV, не распространяются НИКОГДА (MV — это
исключительно триггер на вставку).

**Новый вывод**: `CREATE MATERIALIZED VIEW ... TO <table> POPULATE AS ...`
ОТКЛОНЯЕТСЯ СРАЗУ — `Code: 62. SYNTAX_ERROR: you can't declare both 'TO
[db].[table]' and 'POPULATE'`. `POPULATE` работает только для MV, владеющих
собственным неявным хранилищем (без целевой таблицы `TO`). **Это значит,
что предупреждение задания про «состояние гонки при POPULATE» для данного
push-шаблона неактуально: POPULATE вообще нельзя применить вместе с `TO`,
так что эта конкретная гонка невозможна.** Реальный, проверенно рабочий
рецепт дозагрузки: сначала создать MV БЕЗ POPULATE (новые вставки
начинают течь без разрывов), затем вручную выполнить `INSERT INTO
events_push_dist SELECT * FROM events WHERE <предикат по истории>` для
дозагрузки. Это порождает ДРУГУЮ гонку: любая строка, вставленная между
моментом создания MV и моментом запуска дозагрузочного запроса и
попадающая под предикат дозагрузки, будет отправлена ДВАЖДЫ. Способы
смягчения: ограничить предикат дозагрузки строгой верхней границей по
времени, равной точному моменту создания MV, либо (для таблиц с
естественным ключом дедупликации, как `users_profile`, но НЕ `events` в
этой схеме) полагаться на `ReplacingMergeTree` + `FINAL` на стороне ext.

### 4.4 Рост очереди Distributed и сценарий заполнения диска — измерения

При выключенном ext `system.distribution_queue` росла линейно: около
41,3 KiB на пакет в 2 000 строк (~20,6 байт на строку в формате файла
очереди для этой схемы); отдельная разовая вставка 50 000 строк увеличила
каталог очереди ровно на 1 011 088 байт (~20,2 байт на строку, что
согласуется с предыдущим замером). **В экстраполяции на заданную в
техзадании нагрузку 30 000–100 000 строк/с это даёт от ~600 КБ/с до
~2 МБ/с НЕОГРАНИЧЕННОГО роста диска на MAIN за каждую секунду
недоступности ext** — при этом `bytes_to_throw_insert` и
`bytes_to_delay_insert` в этой версии по умолчанию равны `0` (отключены).
Обе настройки подтверждённо существуют и работают (по официальной
документации и по результатам эксперимента), но их можно задать ТОЛЬКО во
время `CREATE TABLE`: `ALTER TABLE ... MODIFY SETTING` на таблице
`Distributed` завершается ошибкой (`Code: 48. NOT_IMPLEMENTED`).

**Самый опасный вывод всего этого исследования**: таблица
`events_push_dist` была пересоздана с `bytes_to_throw_insert=2000000,
bytes_to_delay_insert=500000`. При выключенном ext вставки сверх порога
приводили к видимым клиенту исключениям (`Code: 574.
DISTRIBUTED_TOO_MANY_PENDING_BYTES`) в 6 из 8 тестовых пакетов — но
**строки всех 8 пакетов (160 000 в сумме) подтверждённо присутствовали в
ИСХОДНОЙ таблице `events` на main независимо от исключения.** Отправка
данных через MV в таблицу Distributed отклоняется УЖЕ ПОСЛЕ того, как
строка надёжно записана в исходную таблицу; локальная запись НЕ
откатывается, когда целевой объект MV ниже по потоку бросает исключение. С
точки зрения клиента это выглядит ровно как неудавшийся INSERT, и
естественная (правильная, общепринятая в индустрии) реакция на
кажущийся сбой INSERT — повторить запрос, что незаметно приведёт к
ДВОЙНОЙ записи этого пакета в ОСНОВНУЮ продакшн-таблицу, а не только в
отправляемую копию, поскольку блочная дедупликация вставок в ClickHouse не
работает между независимо выполненными операторами INSERT с разными
литеральными данными. **Для всех, кто внедряет S3, это должно быть жёстким
эксплуатационным предупреждением, а не сноской.** Второй, связанный
пробел: 120 000 строк из 6 отклонённых пакетов нигде не поставлены в
очередь на автоматическую повторную отправку после возвращения ext — они
навсегда остаются ТОЛЬКО на main; закрывать этот разрыв оператору
придётся вручную.

### 4.5 Изоляция

Схема структурно требует, чтобы main мог открывать исходящие соединения к
ext (push-модель). Нижележащий Docker bridge (как и любая типичная сеть
L3) по умолчанию двунаправлен, поэтому ext ТОЖЕ может достучаться до main,
если отдельно не введено направленное правило файрвола (та же оговорка об
ограниченном тестировании из-за `br_netfilter`, что и в S1; см. §7). Это
худшее сетевое положение по умолчанию среди всех протестированных
сценариев, поскольку сторона, ИНИЦИИРУЮЩАЯ соединение (main, то есть более
чувствительная), делает исходящие вызовы, а способность вызываемой стороны
позвонить в обратную сторону — это обязательство на уровне файрвола, а не
гарантия протокола.

## 5. S9 — эталон антипаттерна (только Distributed, без репликации)

### 5.1 Топология

Main (один узел, таблица `events` на 5 000 000 строк) + ext (один узел, НИ
ОДНОЙ локальной таблицы, НИКАКОГО подключения к Keeper — только
`Distributed(main_from_ext, testgame, events, rand())`).

### 5.2 Количественная оценка цены нулевой изоляции

| Условие | Задержка запросов на main |
|---|---|
| Базовый уровень | 0,046 с |
| Во время 6 параллельных запросов с полной сортировкой таблицы со стороны ext (окно ~35 с) | 0,887 с / 0,999 с / 1,377 с / 1,498 с / 0,892 с |
| После бомбардировки | 0,092 с, возвращается к ~0,05 с |

**Коэффициент деградации: примерно 20–33× от базовой задержки.** Каждый
запрос к таблице Distributed на ext выполняется на CPU, памяти и дисковом
вводе-выводе самого main — здесь нет вообще никакой границы по процессам
и ресурсам, в отличие от всех остальных протестированных сценариев.
`INSERT INTO events_dist` со стороны ext прошёл успешно и достиг main в
течение 2 секунд под пользователем по умолчанию с пустым паролем —
изоляция по записи отсутствует по построению; потребовалось бы то же
исправление с профилем readonly, что и в S1, но без каких-либо реальных
преимуществ S1 по изоляции данных и ресурсов взамен. Полная остановка main
сделала ext на 100% неработоспособным (`Code: 279.
ALL_CONNECTION_TRIES_FAILED`) — диаметрально противоположно плавной
деградации во всех остальных сценариях.

**Это и есть та самая количественная «цена бездействия», которую требовало
задание.**

## 6. S7 — ALTER TABLE ... FETCH PARTITION + ATTACH

### 6.1 Топология

Main + ext в разных сетях; ext получает ТОЛЬКО запись
`auxiliary_zookeepers`, указывающую на Keeper кластера main (доступ на
чтение к дереву znode кластера main, без членства в нём), плюс
совпадающие `interserver_http_credentials` для аутентификации собственно
HTTP-вызовов получения частей.

### 6.2 Механизм подтверждён, найден эксплуатационный подводный камень

`ALTER TABLE events FETCH PARTITION 'x' FROM 'main_keeper:/clickhouse/tables/1/testgame/events'`
помещает часть в каталог `detached/`; последующий `ALTER TABLE events
ATTACH PARTITION 'x'` делает её активной. Работоспособность подтверждена
как для закрытой исторической партиции (3 121 строка, 0,25 с), так и для
«живой», продолжающей принимать вставки партиции (110 479 строк на момент
получения). Повторный запуск цикла после появления новых вставок на main
корректно подхватил дельту (110 479 → 110 979, точное совпадение с main)
БЕЗ дублирования — при условии, что FETCH сразу же сопровождается ATTACH в
рамках одного эксплуатационного цикла.

**Найденный подводный камень**: если цикл прерывается между FETCH и ATTACH
(падение скрипта или оператор запустил FETCH дважды до присоединения), то
ВТОРОЙ FETCH завершается ошибкой: `Code: 256. PARTITION_ALREADY_EXISTS:
Detached partition 20260819 already exists` — FETCH отказывается
перезаписывать уже существующую отсоединённую часть с тем же именем.
Восстановление требует `ALTER TABLE ... DROP DETACHED PARTITION`, который
сам по себе закрыт настройкой `allow_drop_detached` (по умолчанию
отклоняется: `Code: 344. SUPPORT_IS_DISABLED`, требуется явное
`SETTINGS allow_drop_detached=1`). **Любой периодический скрипт
FETCH+ATTACH обязан рассматривать эту пару как единую атомарную операцию с
собственной очисткой после сбоя, иначе один пропущенный цикл заклинит все
последующие обновления этой партиции** — реализовано в
`scripts/fetch_partition_cycle.sh` (шаблон «очистка перед fetch»).

### 6.3 Связанность — уже, чем у S1, шире, чем у S6

Ext требуется (а) сетевая доступность клиентского порта Keeper кластера
main (доступ к znode только на чтение через `auxiliary_zookeepers`) и
(б) доступность interserver-порта HTTP кластера main (9009) с общими
учётными данными; оба канала ИНИЦИИРУЮТСЯ СО СТОРОНЫ EXT (pull-модель, то
же безопасное направление, что и у S6). Ext НИКОГДА не пишет znode под
путём реплицируемой таблицы main и никогда не виден в `system.replicas` на
main — никакого членства в наборе реплик, никакой сессии Keeper, которую
можно потерять, и никакой очистки через `SYSTEM DROP REPLICA`, если ext
исчезнет навсегда, что даёт реальное эксплуатационное упрощение по
сравнению с S1. Тест изоляции показал тот же результат «ext может
достучаться до main напрямую по общей сети для fetch», что и в S1/S3, —
это требуется для самого interserver-pull, а не является случайностью
топологии; здесь нужен тот же разговор о принудительном применении правил
файрвола, что и в §7.

## 7. Сетевая изоляция: что было проверено, а что нет

Три разных вывода, которые нельзя смешивать:

1. **Настоящая, проверенная сетевая изоляция** (S6, после исправления в
   §3.5): контейнеры в полностью непересекающихся сетях Docker вообще не
   могут разрешить имена друг друга или проложить маршрут — это
   обеспечивается самой моделью сетевых пространств имён Docker, а не
   netfilter. Этот факт безусловно реален и был напрямую
   продемонстрирован (DNS_ERROR, отказ соединения).

2. **Структурно необходимая двунаправленная достижимость** (S1 §2.8,
   S3 §4.5, S7 §6.3): механизмы, в которых ЛЮБАЯ из сторон должна
   инициировать исходящие соединения к другой, неизбежно находятся в
   сегменте сети, который по умолчанию разрешает достижимость в обе
   стороны (любой типовой Docker bridge или подсеть облачной VPC). Чтобы
   ограничить это точным перечнем объявленных портов, требуется явное
   правило файрвола (цепочка iptables `DOCKER-USER` локально; security
   groups / NACL в облачных развёртываниях).

3. **Ограничение песочницы, а НЕ вывод о ClickHouse**: в ядре этой
   песочницы отсутствует модуль `br_netfilter` (`cat
   /proc/sys/net/bridge/bridge-nf-call-iptables` → «No such file»),
   поэтому правила iptables `DOCKER-USER` DROP/ACCEPT НИКАК не влияли на
   трафик между двумя контейнерами в ОДНОЙ bridge-сети — подтверждено:
   правила корректно отображались в `iptables -L`, но заблокированный порт
   всё равно оставался доступен. Загрузка `br_netfilter` требует
   привилегированного контейнера с `--pid=host`, выполняющего `modprobe`,
   то есть действия, затрагивающего ядро хоста и требующего явного
   одобрения пользователя; такое одобрение было запрошено, но не получено
   в течение сессии, поэтому был выбран более безопасный вариант по
   умолчанию (не менять ядро хоста). **На любом реальном Linux-хосте с
   Docker и загруженным `br_netfilter` (что является нормой для
   большинства стандартных дистрибутивов с cloud-init) правила iptables
   `DOCKER-USER` в том виде, в каком они написаны в
   `scripts/firewall_s1.sh`, ДЕЙСТВИТЕЛЬНО обеспечивают ограничение портов
   между контейнерами** — это официально документированный механизм
   Docker. Синтаксис и порядок правил были проверены в этой сессии;
   сквозное применение — нет, и отчёт прямо об этом говорит, вместо того
   чтобы заявлять о результате, который на самом деле не наблюдался.

## 8. Runbook для рекомендуемых вариантов

### 8.1 Внедрение S1 (когда нужна свежесть данных в реальном времени)

1. Убедиться, что целевые таблицы используют `ReplicatedMergeTree` с
   ЯВНЫМ литеральным zoo_path (без `{uuid}`) — мигрировать существующие
   таблицы с «голым» `ReplicatedMergeTree` на явный zoo_path ДО попытки
   добавить реплику ext («голая» форма не может безопасно поддерживать
   этот шаблон; см. §2.2).
2. Поднять узлы ext с совпадающими значениями макроса `{shard}` и
   РАЗЛИЧАЮЩИМИСЯ значениями `{replica}`, направив их на ТОТ ЖЕ ансамбль
   Keeper, что и main.
3. Создать таблицу на ext идентичным оператором `CREATE TABLE` (тот же
   zoo_path, та же схема) — `ON CLUSTER` не требуется, ext
   регистрируется автоматически.
4. Немедленно применить выделенный профиль `readonly=1` и квоту к любому
   пользователю, который будет подключаться снаружи; явно выполнить
   `REVOKE SELECT ON system.zookeeper` для этого пользователя (обнаружено,
   что таблица доступна на чтение по умолчанию даже при `readonly=1`,
   §2.3).
5. Установить `insert_quorum=auto` (никогда не фиксированное число,
   включающее реплики ext) для любого писателя, полагающегося на
   подтверждение кворумом.
6. Настроить `interserver_http_credentials` одинаково с обеих сторон до
   того, как открывать любой сетевой путь interserver.
7. Мониторинг: `system.replicas.active_replicas` против `total_replicas`
   (расхождение = мёртвая реплика, требующая разбирательства или
   `SYSTEM DROP REPLICA`), размер `system.replication_queue` (накопление
   при длительной недоступности ext), `absolute_delay` (свежесть).
8. **Runbook при отказе ext**: временный сбой (короче
   `session_timeout_ms` Keeper) не требует действий, восстанавливается
   автоматически. Безвозвратная потеря: `SYSTEM DROP REPLICA` на main,
   затем на «осиротевшем» узле (если он когда-либо восстановится):
   `DROP TABLE ... SYNC` + `CREATE TABLE` с ТЕМ ЖЕ zoo_path и АКТУАЛЬНОЙ
   схемой (со всеми применёнными с тех пор ADD COLUMN), полное
   перекачивание данных с нуля.

### 8.2 Внедрение S6 (когда нужна максимальная изоляция)

1. Развернуть main и ext БЕЗ единой общей сети Docker / подсети VPC /
   security group — проверить это реальным тестом связности между узлами
   (вывод из теста изоляции в §3.5 показывает, почему это нужно
   проверять, а не предполагать).
2. Направить обе стороны на ОДИН И ТОТ ЖЕ S3-бакет/endpoint по
   непересекающимся сетевым путям (эталонный образец — исправленная
   топология из §3.5); если объектное хранилище это поддерживает, выдать
   раздельные политики бакета / учётные данные IAM: только на чтение для
   ext и на чтение-запись для main (отдельно в этом проходе не
   тестировалось; отмечено как мера усиления защиты, с той же оговоркой
   про общие пустые учётные данные, что и в других местах отчёта).
3. Настроить расписание `BACKUP DATABASE ... TO S3(...) SETTINGS
   base_backup=<предыдущий>` с частотой, соответствующей допустимому окну
   устаревания данных; отслеживать `system.backup_log` по динамике
   длительности и размера и настроить алерты на аномальный рост (эффект
   раздувания из-за мутаций, §3.2).
4. Для обновления «горячего хвоста» конкретной ещё открытой партиции
   использовать проверенно рабочий рецепт: `ALTER TABLE ... DROP
   PARTITION 'x'` на ext, ЗАТЕМ `RESTORE TABLE ... PARTITIONS 'x' ...
   SETTINGS allow_non_empty_tables=1` — а НЕ шаблон с временной таблицей
   и REPLACE PARTITION, который не работает так, как описано в
   документации, для `ReplicatedMergeTree` с литеральным zoo_path (§3.3).
5. **Runbook при отказе ext**: уже восстановленные данные на ext полностью
   независимы; безвозвратная потеря ext требует лишь развернуть новый узел
   и заново прогнать последнюю цепочку RESTORE (полный + инкрементальные)
   — main при этом не задействован ни в чём, кроме обслуживания расписания
   бэкапов.

## 9. Не тестировалось (S2, S4, S5, S8) — задокументировано, но не выдумано

Согласно приоритетам и рекомендациям по бюджету из самого задания
(«четыре сценария с измерениями лучше девяти с допущениями»), эти варианты
были изучены только по документации и НЕ собирались:

- **S2 — база данных `ENGINE=Replicated` + `replica_group_name`**: по
  официальной документации
  (`clickhouse.com/docs/reference/engines/database-engines/replicated`)
  база данных `Replicated` разделяет область репликации ДАННЫХ через
  `replica_group_name`, тогда как репликация DDL остаётся общей для всего
  пути базы данных в Keeper — но независимо в этой сессии это НЕ
  проверялось. Отмечено как естественный следующий эксперимент: возможно,
  этот вариант автоматически снимает ту самую проблему zoo_path/`{uuid}`
  из §2.2 (движок базы данных `Replicated` по замыслу сам обеспечивает
  согласование UUID между репликами), сохраняя при этом оговорку S1 об
  изоляции по записи, поскольку участники группы реплик остаются
  полноправными репликами нижележащих таблиц. Не тестировалось.
- **S4 — Refreshable Materialized View (`REFRESH EVERY`)**: не собиралось.
  По документации известно, что перед использованием нужно проверить флаг
  зрелости этой возможности в конкретной версии; статус GA/experimental в
  этой сессии независимо не подтверждался, поэтому никаких утверждений в
  ту или иную сторону не делается.
- **S5 — периодический `INSERT INTO FUNCTION remoteSecure(...) SELECT` по
  партициям**: не собиралось. Вопрос pull против push и идемпотентности
  через промежуточную таблицу прямо аналогичен выводам S7 (§6.2) и
  проблеме с временной таблицей в S6 (§3.3) — вероятно, здесь возникнут
  схожие сложности, но это умозаключение, а не измерение, и подаётся
  именно так.
- **S8 — общий S3 zero-copy / `s3_plain_rewritable` / web-диск только на
  чтение**: не собиралось. В собственной документации ClickHouse эти
  возможности на момент данной версии явно помечены как
  экспериментальные / не рекомендованные для продакшена; дальше не
  изучались согласно указанию задания понижать приоритет
  экспериментальных функций.

## 10. Риски и то, чего это решение НЕ даёт

- **Ни один штатный механизм не обеспечивает одновременно свежесть данных
  в реальном времени И полную сетевую изоляцию с изоляцией по записи.**
  Любой выбор — компромисс по этой оси; см. сравнительную матрицу в
  README.
- **Изоляция по записи в S1 целиком является свойством уровня
  пользователей/профилей, а не свойством топологии репликации.**
  Неправильно настроенный или скомпрометированный пользователь ext пишет
  прямо в продакшен. Это не гипотеза: такое было напрямую воспроизведено в
  ходе исследования (§2.3).
- **Режим отказа S3 при длительной недоступности ext опасен по
  умолчанию** (неограниченный рост диска), а после ограничения через
  `bytes_to_throw_insert`/`bytes_to_delay_insert` порождает ДРУГОЙ опасный
  режим отказа: видимые сбои вставок, которые на самом деле успешно прошли
  в исходную таблицу, что провоцирует повторные попытки, незаметно
  создающие дубликаты (§4.4). Это самый рискованный из оценённых в проекте
  механизмов.
- **«Инкрементальные» бэкапы S6 не пропорциональны реальному объёму
  изменений данных**, когда мутации или `OPTIMIZE FINAL` затрагивают уже
  сохранённые партиции (§3.2) — закладывайте в бюджет скачки стоимости в
  дни мутаций, а не только стационарный режим.
- **`system.zookeeper` по умолчанию доступна на чтение пользователю с
  `readonly`** (обнаружено в S1, §2.3) — настоящая, легко упускаемая брешь
  в изоляции, которую нужно явно отзывать, а не считать закрытой по
  умолчанию через `readonly=1`.
- **Применение iptables/файрвола для требования «узкий список разрешённых
  портов» НЕ было проверено сквозным тестом** в этой песочнице из-за
  отсутствующего модуля ядра (§7) — это пробел в тестировании ИМЕННО ЭТОГО
  окружения, а не утверждение о неработоспособности механизма в
  продакшене; но это означает, что отчёт не может заявлять о личной
  проверке уровня файрвола, только о проверке механизмов уровня
  приложения.
- **Ни один из протестированных механизмов штатно не обеспечивает отбор
  подмножества по колонкам или строкам.** S1 требует идентичной таблицы;
  S3/S6/S7 могут выставлять ДРУГУЮ таблицу (например, курируемое
  представление, материализованное в собственную таблицу), но это
  требует дополнительного слоя, который строит оператор, а не встроенного
  фильтра.

## 11. Что меняется в продакшене

- **Разные ЦОД / задержки до Keeper**: S1 и S2 требуют, чтобы задержка
  round-trip до Keeper для внешней реплики оставалась в допустимых
  пределах для heartbeat-сессий (`session_timeout_ms`) и опроса лога
  репликации; задержки Keeper между ЦОД/регионами (десятки мс) — это
  принципиально другой режим по сравнению с субмиллисекундной сетью Docker
  на одном хосте в этой песочнице, и в условиях реалистичных задержек WAN
  оценка не проводилась.
- **TLS / interserver-учётные данные**: в продакшене ОБЯЗАТЕЛЬНО включать
  `interserver_https_port` (а не только HTTP + общий пароль, как
  использовалось в этой песочнице ради простоты) и TLS на нативном и
  HTTP-портах клиента для любого трафика, пересекающего недоверенный
  сегмент сети.
- **Правила файрвола**: точные списки портов, задокументированные для
  каждого сценария (§2.8 для S1: Keeper 9181 + interserver 9009; S3/S7:
  interserver 9009 + Keeper 9181 по применимости; S6: только endpoint S3),
  должны применяться реальными правилами файрвола / security groups — в
  этом проекте проверена корректность написания правил (§7), но не их
  реальное применение.
- **ACL для Keeper**: в этой песочнице не настраивались вообще (по
  умолчанию ClickHouse Keeper разрешает любому аутентифицированному
  соединению полный доступ на чтение и запись к любому znode, до которого
  оно достаёт). В продакшене следует настроить собственные ACL Keeper,
  ограничивающие, какие учётные данные могут читать и писать какие
  поддеревья znode, особенно для трансграничного доступа к Keeper в
  S1/S7.
- **RBAC и квоты**: в этой песочнице в ряде сценариев (S3, S9)
  использовался единственный общий пользователь `default` с пустым
  паролем — исключительно ради простоты тестов; в продакшене так делать
  нельзя никогда: каждому пользователю, работающему извне, нужны
  собственные учётные данные, профиль `readonly` и квота, как это сделано
  для `ext_reader` в S1 (§2.3), и применять это следует одинаково
  независимо от выбранного сценария.
- **Ёмкость**: расчёты роста очереди в S3 (§4.4, наблюдалось ~20 байт на
  строку для этой схемы) и рост znode в Keeper для S1 под постоянной
  нагрузкой измерялись только на малом масштабе; планирование ёмкости для
  продакшена при 30–100 тыс. строк/с должно экстраполировать эти цифры
  аккуратно и предусматривать запас по диску на MAIN (а не только на ext)
  для роста очередей и логов любого push-механизма или механизма на основе
  реплик во время длительного простоя внешней стороны.
